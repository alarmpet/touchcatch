## 0. 한 줄 판단

보고서의 결론은 "AR 말고 `Alive Difference`부터"다. 이 판단은 우리에게 특히 맞는데,
이유가 보고서가 말한 것과 조금 다르다.

보고서는 이걸 **연출 문제**로 본다. 우리에게 이건 **콘텐츠 파이프라인 문제**다.

`CLAUDE.md`에 이미 기록돼 있듯 기존 79개 팩 중 25개(32%)가 플레이 불가였고, 원인은 전부
"B를 A의 편집이 아니라 비슷한 프롬프트로 새로 생성"이었다. 보고서가 권하는
**Master Scene + Difference Metadata** 구조는 그 사고를 구조적으로 불가능하게 만드는
설계다. 즉 우리에게 이 항목은 "예쁘게 만들자"가 아니라 **"팩의 3분의 1이 죽는 걸 막자"**다.

그래서 우선순위를 이렇게 잡는다.

```
지금 열린 문 닫기 → 콘텐츠 파이프라인 → 발견의 0.5초 → 리텐션 루프 → 소셜 → 수익화
     (P0-0)          (P0-1)            (P0-2)         (P1)        (P2)      (P3)
```

> **v1.1 갱신 (2026-08-14):** "찾기 → 글자 리빌"과 "랜드마크 씬 패밀리" 두 안을
> 검토해 반영했다. 각각 §5.6, §4에 있다.
>
> **v1.2 정정 (2026-08-14):** v1.1이 §5.6을 "신규 제안"으로 적은 것은 **오류였다.**
> 그 기능은 캐주얼 경로에 이미 구현돼 있다. 코드를 확인하고 §5.6을 다시 썼다.
> 실제로 비어 있던 것은 **리빌 규칙이 정책에 고정돼 있지 않다**는 점이었고 (완료),
> 그 과정에서 **랭크드 보드가 아직 플레이 불가**라는 더 큰 구멍이 드러났다 (§12).
>
> **v1.3 (2026-08-14):** §12를 서버 권위 탭으로 구현했다. 마이그레이션
> `202608140002`. 부수적으로 `wrong_taps`가 클라이언트 선언값에서 탭 로그 파생으로
> 바뀌어, 첫 배선 때 남겨둔 신뢰 경계 하나가 닫혔다.

## 2. 스택 번역 — 보고서를 그대로 못 쓰는 부분

보고서는 Unity 6 + UGS + Firebase를 전제한다. 우리는 아니다. 다음은 **번역하거나 버려야
하는** 지점이다.

| 보고서 | 그대로 쓸 수 없는 이유 | 우리 대응 |
|---|---|---|
| Unity URP / Particle System | RN에는 없음 | 정답 FX는 Reanimated + (필요시) Skia. 파티클은 스프라이트 몇 개로 흉내 |
| Addressables CDN | Unity 전용 | Supabase Storage + 기존 `content/` sha256 매니페스트 그대로 |
| Unity Gaming Services | 백엔드 중복 | **버림.** 리더보드/시즌/시도는 이미 Postgres에 있음 |
| Firebase Remote Config / A-B | 새 SDK 도입 | `config/*.v1.json` + 승인 해시 체계가 이미 Remote Config 역할. A/B는 `assignExperimentVariant()` 존재 |
| AR Foundation | Expo Go에서 불가, 별도 네이티브 빌드 필요 | **v2 이후로 보류.** 아래 §7 참조 |
| RevenueCat | 도입 가능하나 시기상조 | 광고 제거 1회 구매만 먼저 |
| Firebase Analytics 이벤트 스키마 | **우리 개인정보 계약과 충돌** | §6에서 재설계 |

### 특히 주의: 보고서의 analytics 스키마는 우리 계약을 통과하지 못한다

`packages/contracts/src/analytics.ts`의 `privacyScan`은 필드명에
`coordinate`, `timestamp`, `answer`, `objectiveId`, `x`, `y`, `correctness`가 들어가면
**던진다.** 보고서가 제안한

```
difference_found { level_id, difference_id, elapsed_ms, order }
```

는 `difference_id`가 사실상 objectiveId라 그대로는 못 보낸다. 의도적인 설계이고,
우회할 게 아니라 **버킷 지표로 다시 설계**해야 한다. §6에 대안을 적었다.

## 3. P0 — 지금 열려 있는 문부터 닫는다

랭크드 제출 경로는 오늘 배선을 마쳤다. 남은 것은 그 경로가 **실제로 화면에 닿게** 하는 일이다.

### P0-0-a. 마이그레이션 검증

`supabase/migrations/202608140001_learning_attempt_ownership.sql`는 Postgres 문법
파서로만 확인했다. Docker가 있는 환경에서 아래를 돌려야 한다.

```bash
pnpm check:db     # supabase db reset + lint + pgTAP
```

확인 사항 두 가지:

- `economy_server`가 `attest_learning_assets_ready_v1` / `commit_learning_attempt_v1`
  **직접 호출에 실패**해야 한다 (owned_ 래퍼로만 가능)
- 남의 `attempt_id`로 owned_ 래퍼를 부르면 `ATTEMPT_NOT_FOUND`

pgTAP에 이 두 케이스를 추가하는 것이 이 단계의 산출물이다.

### P0-0-b. 학습 화면 → 랭크드 세션 연결

`ranked-session-controller.ts`는 만들었지만 화면이 아직 부르지 않는다. 붙일 자리:

```
apps/mobile/app/game/spot-difference.tsx      ← 지금은 __DEV__ 프리뷰만
apps/mobile/src/learning-demo/LearningDemoScreen.tsx
```

주의: `production-boundary.test.ts`가 `preview-registry`에 `contentRevisionId`가
들어가는 것을 금지한다. 따라서 랭크드 모드는 **preview 팩이 아니라
`GET /v1/learning/challenges` 응답으로만** 보드를 구성해야 한다. 두 경로를 한 화면에서
분기시키되, 랭크드 분기가 프리뷰 레지스트리를 절대 읽지 않도록 한다.

### P0-0-c. 정책 승인

현재 `config/hint-policy.v1.json`과 `config/weekly-competition.v1.json`이 DRAFT라
프로덕션에서 랭크드가 닫혀 있다(409 `HINT_POLICY_NOT_APPROVED`). 승인 절차를 밟기 전엔
로컬 픽스처로만 돌아간다. 이건 버그가 아니라 의도된 fail-closed다.

## 4. P0-1 — 콘텐츠 파이프라인 (가장 높은 ROI)

보고서 §"콘텐츠 제작 파이프라인"을 우리 문제에 맞춰 옮긴다.

### 지금 구조의 문제

현재 팩은 **완성된 두 장의 이미지 + 손으로 적은 좌표**다. 그래서:

- A와 B를 따로 만들면 조명·질감이 전부 달라져 화면 전체가 "다른 곳"이 된다
- 실제 찾을 수 있는 덩어리는 몇 개 안 되고 판이 안 끝난다 (`en-dilemma`: 화면의 10.8%가
  달랐는데 찾을 수 있는 차이는 1개)
- `content:hitboxes:derive`가 사후에 이걸 잡아내지만, **이미 만든 뒤**다

### 목표 구조

```
Master layered scene (레이어별 PNG + layout.json)
        ↓
Difference Variant = 마스터의 레이어 N개만 조작한 선언
  ├ 색상 시프트
  ├ 회전 / 이동
  ├ 숨김
  ├ 크기
  └ 소품 교체
        ↓
빌드 시 A/B 두 장을 같은 파이프라인으로 렌더
        ↓
차이 영역은 계산이 아니라 선언에서 나옴 (derive는 검증용으로 강등)
        ↓
난이도 태그 + 팩 사용 가능 판정
```

**핵심 이득:** "B는 A의 편집이어야 한다"가 규칙이 아니라 **구조적 사실**이 된다.
편집이 주변으로 번지는 사고가 원천 차단된다.

### 실행

| 과제 | 산출물 | 비고 |
|---|---|---|
| 마스터 씬 스키마 정의 | `schemas/master-scene.schema.json` | 레이어 + 변형 선언 |
| 렌더러 | `tools/content/render-scene.mjs` | sharp 등으로 레이어 합성 |
| 기존 79팩 중 살릴 것 선별 | 결정 문서 | 54개만 사용 가능 상태 |
| `derive-hitboxes`를 검증기로 강등 | 기존 스크립트 수정 | 선언 ↔ 실제 픽셀 차이 일치 검사 |
| 난이도 태그 | 크기/중심도/변형종류 | 보고서 §"난이도 태그" 그대로 |

**이 단계를 건너뛰고 2.5D를 하면 안 된다.** 레이어 구조가 없으면 parallax도 못 만든다.
같은 투자가 두 목표를 동시에 산다.

### 랜드마크 씬 패밀리 — 첫 마스터 씬 세트 (신규 제안 B)

> 각 나라·도시의 랜드마크 이미지를 카테고리나 영어단어 쪽에 추가.

**채택. 단, 새 카테고리가 아니라 ENGLISH 안의 씬 패밀리로.**

#### 새 카테고리로 만들면 안 되는 이유

DB가 카테고리를 두 개로 못박아 놨다.

```sql
category text not null check (category in ('ENGLISH','PROVERB'))
enabled_categories text[] not null check (enabled_categories = array['ENGLISH','PROVERB']::text[])
```

`weekly-competition.v1.json`도 `categories`를 튜플 리터럴로 고정한다. 카테고리를 늘리면
마이그레이션 + 정책 해시 변경 + 시즌 재핀이 전부 따라온다. 반면 씬 패밀리는
`publicContent.theme`만 쓰면 되므로 **스키마 변경이 0이다.**

```
en-lm-paris-bridge      정답: BRIDGE
en-lm-kyoto-temple      정답: TEMPLE
en-lm-jeju-lighthouse   정답: LIGHTHOUSE
```

장면은 랜드마크, 정답은 그 장면이 실제로 담고 있는 영어 단어다.

#### 지금 EN 세트의 진짜 문제를 고친다

현재 92개 EN 드래프트는 **추상명사에 몰려 있다** — creativity, harmony, serenity, solitude.
그림 찾기 게임에서 이건 구조적 약점이다.

- 추상명사는 **그릴 수가 없다.** 그림과 정답 사이 연결이 임의적이다
- 그래서 §5.6의 리빌 비행이 착지해도 "왜 이 그림이 creativity지?"가 남는다

랜드마크는 정확히 반대다. tower, bridge, castle, temple, harbor, market, cathedral,
lighthouse, fountain, palace, dome, arch — **그림이 곧 뜻인 구체명사**이고, 사진 기반
어휘 학습이 가장 잘 작동하는 구간이다.

**즉 이건 테마 추가가 아니라 콘텐츠 품질 교정이다.**

#### 나머지 계획과 맞물리는 지점

| 연결 | 내용 |
|---|---|
| 2.5D (§5.7) | 랜드마크는 천성적으로 레이어드다 — 하늘 / 기념물 / 중경 / 전경 인파. parallax 소재로 최적 |
| 여행 지도 (§6.3) | 보고서가 권한 `서울 → 제주 → 도쿄 → 파리` 진행이 자연스럽게 나온다. 화폐를 늘리지 않고 축을 하나 얻는다 |
| variant 재활용 | 한 씬을 `낮 / 비 / 야간 / 겨울`로 재활용. 보고서의 "Hero 30~50 + 일반 100~200 + variant" 구조 |
| 리빌 비행 (§5.6) | 구체명사라 착지한 글자가 그림과 즉시 연결된다 |
| 시장 근거 | Metajoy `Difference Find Tour`가 여행 사진만으로 1,000만+ 다운로드 |

#### 권리 문제 — 여기가 진짜 위험이다

랜드마크에는 **두 겹의 권리**가 있다. 사진의 저작권과, 건축물 자체의 저작권이다.
후자를 푸는 게 파노라마의 자유(freedom of panorama)인데, **나라마다 다르고 몇몇
주요 관광국이 가장 빡빡하다.**

| 지역 | 상태 | 실무 결론 |
|---|---|---|
| 프랑스 · 이탈리아 · 벨기에 | FoP 예외를 국내법에 도입하지 않음 | **현대 건축물 회피.** 에펠탑은 주간 구조물 자체는 PD이나 **1985년 야간 조명 연출은 별도 저작물** |
| 그리스 | FoP 제한 + **고대 유적 촬영에 정부 라이선스·수수료** 별도 법 | 파르테논 등은 라이선스 없이 상업 이용 불가 |
| 그 외 | 나라별 상이 | 개별 확인 |

**일러스트로 그리면 사진 저작권은 피하지만 건축 저작권은 피하지 못한다.** FoP가 없는
나라의 현대 건축물은 스타일라이즈해도 위험이 남는다.

안전한 출발 세트:

1. **자연 랜드마크** — 저작권 자체가 없다 (한라산, 후지산, 그랜드캐니언)
2. **저작권 만료 구조물** — 오래된 성·다리·등대·시장
3. **FoP가 넉넉한 나라의 현대물** — 개별 확인 후
4. **가상 도시** — "파리풍 골목"이되 실재 건물이 아님. 가장 안전하고 아트 자유도도 높다

우리에겐 이미 걸어둘 게이트가 있다. 학습 드래프트의 `rightsReviewStatus`,
그리고 펫 아트 쪽 `config/pet-rights-evidence.v1.json` +
`runtimeArtRightsEvidenceIsApproved` 패턴을 랜드마크 세트에 그대로 적용한다.

> 이 절은 리스크 체크리스트이며, 실제 출시 전에는 대상 국가 법률 검토가 필요하다.

#### 제작상의 함정

| 함정 | 대응 |
|---|---|
| **AI 아트 위험이 특히 크다** | 사람들은 에펠탑이 어떻게 생겼는지 안다. 뭉개지면 "스타일"이 아니라 "고장"으로 읽힌다. 간판 글자 깨짐도 흔하다. 보고서의 Yolo 사례가 그대로 재현될 자리 |
| 대칭·반복 구조에 차이를 두면 못 찾거나 너무 쉽다 | 차이는 **기념물이 아니라 주변에** — 노점, 새, 간판, 배, 가로등, 인파 |
| 종교 시설 | 문화적 민감도 검수 |
| 실존 인물 얼굴 | 넣지 않는다 |

#### 실행 순서

랜드마크 세트를 **P0-1 마스터 씬 파이프라인의 첫 고객으로** 삼는다. 신규 세트라
기존 79팩처럼 "A와 B를 따로 만든" 부채가 없고, 처음부터 레이어드로 만들 수 있다.
목표: 마스터 씬 10개 → variant 포함 30개 보드.

#### 정정 — 이건 이미 만들어져 있다

**v1.1에서 이 절을 "신규 제안"으로 적었는데 틀렸다.** 코드를 열어보니 캐주얼(학습 데모)
경로에는 처음부터 끝까지 구현돼 있다.

| 조각 | 위치 |
|---|---|
| 비행 모델 (`LetterFlight`, `FLIGHT_MS` 560ms, `SLOT_POP_MS`) | `apps/mobile/src/learning-demo/feedback-model.ts` |
| 리빌 예산 (`answerUnits`, `newlyOpenedUnitIndex`) | `apps/mobile/src/features/answer-modes/answer-mode.ts` |
| 비행 연출 + 슬롯 측정 + 착지 팝 | `apps/mobile/src/learning-demo/LearningDemoScreen.tsx` |
| `assistPattern: 'SPELLING' \| 'INITIAL_PATTERN' \| 'NONE'` | `apps/mobile/src/learning-demo/data.ts` |
| 테스트 | `apps/mobile/src/features/answer-modes/answer-mode.test.ts` |

동작도 정확하다. 영어는 찾기 1개당 글자 1개, 한국어는 초성부터 열고 초성이 다 열리면
음절로 승급한다. **그리고 이 절이 "반드시 지켜야 할 규칙"이라고 적은 것을 이미 지키고
있다** — `Math.max(0, letters - 1)`, `Math.max(0, total - 1)`로 마지막 단위를 절대
열지 않는다. 코드 주석에도 같은 논거가 적혀 있다.

> 슬롯을 향해 날아가는 글자가 아직 도착하지 않았으면 그 칸은 비어 있다.
> 탭하는 순간 채우면 비행이 장식이 된다 — 요점은 비행이 **배달한다**는 것이다.

**따라서 이 절의 남은 일은 연출이 아니라 두 가지다.**

#### 남은 일 1 — 리빌 규칙을 정책에 고정 ✅ 완료

리빌 예산이 `answer-mode.ts`의 상수로만 존재하면, 두 빌드가 서로 다른 예산을 쓰는 순간
랭크드 점수가 비교 불가능해진다. 시즌 행이 `hint_policy_hash`를 박아두는 이유가 정확히
그것이다.

`config/hint-policy.v1.json`에 `findReveal` 블록을 추가하고 `answer-mode.ts`가 그 값을
읽도록 바꿨다. 계약(`learning-policy.ts`)이 세 가지를 강제한다.

| 강제 항목 | 이유 |
|---|---|
| `rankedPenaltyPerUnit: 0` | 찾기 리빌은 무료. 유료 트랙은 `ranked.penaltyPerStep: 15000` 하나뿐 |
| `unresolvedTailUnits: 1` | 0을 넣으면 파싱이 실패한다. 판을 다 밀어도 답이 다 안 열린다 |
| `tracks.SPELLING / INITIAL_PATTERN` | 화면 카테고리 분기가 아니라 정책 트랙 |

`hintPolicyHash`가 바뀌었다(`f6fda676…`). 정책이 DRAFT라 아직 시즌에 박히지 않았으므로
비용이 0이다. **승인 후였다면 시즌 재핀 + 기존 시도 전부 `POLICY_MISMATCH`였다.**

#### 남은 일 2 — 랭크드 보드는 아직 이 화면을 못 쓴다

§3에서 만든 `GET /v1/learning/challenges`는 `imageA`/`imageB`만 내려준다.
**차이 좌표도, `hintUnits`도 없다.** 의도적이다 — `hintUnits`는
`["c","r","e","a","t","i","v","i","t","y"]`처럼 답을 그대로 철자한 것이라 절대 못 내보낸다.

그래서 지금 랭크드 클라이언트는 **탭이 맞았는지조차 판정할 수 없다.** 캐주얼 경로가
프리뷰 레지스트리에서 좌표를 읽어 쓰는 것과 달리, 랭크드는 그 데이터를 가질 수 없다.

이건 §3의 배선이 남긴 진짜 구멍이고, 설계 결정이 필요하다. §12에 따로 적었다.

#### 왜 강한가

1. **지금은 두 시스템이 따로 논다.** 차이를 찾으면 점수가 오르고 최종 문제가 열린다.
   그 연결이 추상적이다. 리빌 비행은 인과를 **눈에 보이게** 만든다.
2. **보고서가 지적한 최악의 지표를 직접 공격한다.** "마지막 하나 남기고 포기"가
   왜 생기냐면 막힌 플레이어에게 **출구가 없기** 때문이다. 찾을 때마다 글자가 열리면,
   9개 찾고 1개 못 찾은 사람도 단어를 추측해 판을 끝낼 수 있다. 막다른 길이 사라진다.
3. **효과가 퍼즐을 가리지 않는다.** 보고서의 경고 "효과가 퍼즐을 가림"은 보드 위에
   터지는 파티클 얘기다. 이 연출은 **보드 밖으로 나간다.** 오히려 화면을 비운다.
4. **`feedback-model.ts`에 그대로 얹힌다.** 이미 `Animated` 없는 순수 타이밍 모델이라
   `FLIGHT` 종류와 목적지 슬롯 인덱스만 추가하면 된다. 테스트 결정성도 유지된다.

#### 반드시 지켜야 할 세 규칙

여기서 밸런스를 틀리면 게임이 삭제된다. `controller.ts`의 점수 주석이 이미 같은 함정을
다룬 적이 있다 — "속도 보너스를 가산으로 주면 최적 전략이 '그림을 무시하고 최종 문제가
열리자마자 답하기'가 되어 게임이 사라진다."

같은 논리가 그대로 적용된다.

> **규칙 1. 찾기만으로는 마지막 글자를 절대 열지 않는다.**
> 전부 찾으면 답이 저절로 보이는 순간 최종 문제가 스스로를 삭제한다.

> **규칙 2. 찾기와 힌트는 같은 인덱스를 열지 않는다.**
> 지금 힌트 사다리는 4단계 `[0]`, 5단계 `[1,3,5,7,9]`로 10글자 중 6글자를 연다.
> 찾기가 같은 자리를 열면 15,000점짜리 힌트가 무가치해진다.

> **규칙 3. 리빌은 `claimedIds.length`에서 결정론적으로 파생된다.**
> 그래야 서버가 모델링하지 않아도 같은 팩을 푸는 모든 플레이어에게 공정하다.

이 셋을 만족하는 가장 단순한 배분:

**찾기는 자리(윤곽·초성)를, 힌트는 글자를 준다.**

| | 한국어 (속담) | 영어 (단어) |
|---|---|---|
| 찾기 보상 | 음절별 **초성**을 하나씩 (`ㄷ_ ㅁ_ ㅇ_`) | 글자 수 + 빈칸 자리, 그다음 자음 자리 표시 |
| 힌트 보상 | 실제 음절 | 실제 글자 |
| 상한 | 마지막 음절 초성은 안 염 | 마지막 글자는 안 염 |

한국어 쪽은 이게 그냥 더 낫다. 9음절 속담에서 음절 하나를 통째로 열면 도약이 너무 크지만,
초성만 열면 윤곽만 준다. 한국 퀴즈 프로그램이 수십 년째 쓰는 방식이다.

정확한 리빌 예산은 밸런스 패스가 필요하다. `content:hitboxes:derive`로 팩별 차이 개수가
7~10개로 제각각이라, "차이 N개당 초성 1개"를 고정값이 아니라 비율로 잡아야 한다.

#### 아직 안 붙은 감각 계층

비행은 있는데 손과 귀가 비어 있다. §5.1·§5.3이 여기에 걸린다.

- 착지 순간 햅틱 Light (연속 발견 시 Medium)
- 착지 음이 한 단계씩 상승, 마지막 글자에서 화음 완성
- **Reduce Motion 시 비행 생략**, 글자만 나타난다. 정보는 동일하게 전달된다

#### 남는 위험

| 위험 | 대응 |
|---|---|
| 91개 팩에 `hintLadder`가 없음 | `hintUnits`에서 기계 생성 + 사람 검수. **드래프트를 조용히 고치면 `privateSolutionHash`가 깨진다** — 승인 산출물이므로 해시·매니페스트·승인 동시 갱신 |
| 리빌이 너무 후해 최종 문제가 죽음 | 계약이 `unresolvedTailUnits: 0`을 거부. 추가로 최종문제 정답률 관측 |
| 랭크드 점수 왜곡 | `rankedPenaltyPerUnit: 0` 고정. 힌트가 "일 안 하고 글자 받기"라는 위치를 지킴 |
| 애니메이션이 탭 응답을 늦춤 | 비행은 순수 표현. 리듀서 판정은 즉시 |

## 6. P1 — 리텐션 루프와 계측

### 6.1 계측 먼저

보고서의 가장 실용적인 통찰:

> **"마지막 하나를 못 찾아 포기하는 비율"이 DAU보다 제작팀에게 훨씬 유용하다.**

우리 개인정보 계약을 지키면서 이걸 얻는 방법:

| 보고서 이벤트 | 우리 계약에서 금지 | 대안 |
|---|---|---|
| `difference_found {difference_id, elapsed_ms, order}` | `difference_id`, `elapsed_ms` | `difference_found_signal { ordinalBucket, elapsedBucket }` — 순번은 1/2/3/4/5+, 시간은 기존 `durationBucket` 어휘 재사용 |
| `wrong_tap {elapsed_ms, zoom_bucket}` | 좌표 금지 | 이미 있는 `same_coordinate_burst_signal` 재사용 |
| `level_abandon {remaining_count}` | `remaining_count`는 허용 | **`abandon_signal { remainingBucket }`** — `0`/`1`/`2-3`/`4+`. **1이 우리가 원하는 그 지표** |
| `hint_used {source}` | 허용 | 그대로 |

`abandon_signal`의 `remaining=1` 비율을 팩별로 뽑으면, 어떤 팩의 hotspot이 잘못 설계됐는지
바로 보인다. **이 하나만 붙여도 P0-1 콘텐츠 작업의 우선순위를 데이터로 정할 수 있다.**

### 6.2 서버 고스트

지금 `ghost-model.ts`는 **자기 자신의 기록**과 레이스한다. 정직한 설계이고, 주석에도
"남의 기록인 척하는 건 플레이어가 절대 잡아낼 수 없는 거짓말"이라고 적혀 있다.

오늘 만든 attempt 커밋 경로가 **남의 기록을 정직하게 저장할 자리**를 처음으로 열었다.
`private.learning_attempts`에 이미 `event_digest`가 있고, `completion_ms`와 순서 정보를
확장하면 서버 고스트가 된다.

보고서의 비대칭 논거는 우리에게도 그대로 유효하다:

| Async Ghost | Real-time PvP |
|---|---|
| 대기시간 없음 | 동시 접속 필요 |
| 서버비 낮음 | 높음 |
| 치팅 검증 단순 | 복잡 |

우리는 이미 `07_REALTIME_SERVER_SPEC.md`에 실시간 대전 설계가 있지만, **고스트가 먼저**다.

### 6.3 Daily / Collection

`daily-puzzle.ts`(날짜 파생)와 펫 컬렉션이 이미 있다. 보고서의 "Journey Map"은
**펫 컬렉션이 이미 그 역할**을 하고 있으므로 새로 만들지 않는다. 대신:

- 홈에 시즌 진행 바 (보고서 §추천 홈 UI)

## 7. P2/P3 — 소셜과 수익화

### 7.1 화폐는 늘리지 않는다

보고서 권고: **Stars(진행도) + Magnifier(힌트)** 두 개면 충분하다.

우리는 이미 `economyVersion` / 드로우 포인트 / 펫 XP / 계정 XP가 있다.
`award_learning_progression_v1`도 배선 전이다. **여기서 화폐를 더 늘리면
"쉬운 관찰 퍼즐이 회계 프로그램이 된다"**는 보고서 경고가 정확히 우리 얘기가 된다.

### 7.2 확률형 규제 — 우리는 이미 안전한 쪽

보고서는 확률형 유료 아이템을 피하라고 한다. 우리 가챠(`claim_daily_free_draw_v1`)는
**무료 일일 뽑기**라 유료 확률형 규제 대상이 아니다. 이 구분을 유지한다:

> **뽑기는 무료로만. 돈을 받는 상품은 무엇을 받는지 정확히 보이는 것만.**

### 7.3 수익화 순서

## 12. 랭크드 보드 — 서버 권위 탭 ✅ 구현 완료

§3에서 시도 제출 경로를 배선하면서 드러난 구멍이었다. **(a)안으로 해결했다.**

### 문제

| 경로 | 차이 좌표를 어디서 얻나 | 상태 |
|---|---|---|
| 캐주얼 (학습 데모) | `preview-registry.generated.ts` — 파생된 히트박스가 번들에 들어 있음 | 동작 |
| **랭크드** | **없음** | **탭 판정 불가** |

`GET /v1/learning/challenges`는 `imageA`/`imageB`만 준다. 의도적이다 —
`private.game_content_solutions`를 건드리지 않는 것이 이 엔드포인트의 안전성 근거다.
`hintUnits`도 못 내보낸다. `["c","r","e","a","t","i","v","i","t","y"]`는 답 그 자체다.

즉 랭크드 클라이언트는 **탭이 맞았는지 알 수 없고, 정답 슬롯도 그릴 수 없다.**

### 선택지

| 안 | 방식 | 장점 | 비용 |
|---|---|---|---|
| **(a) 탭 명령 엔드포인트** | `POST /attempts/{id}/tap` → 서버가 hit/miss + 열린 유닛 반환 | 완전한 서버 권위. 대전 엔진이 이미 쓰는 방식 (`projectSnapshot`은 **이미 획득한** 목표의 원만 내려준다) | 판당 10~15회 왕복. 오프라인 불가. 지연이 체감됨 |
| (b) assets-ready 시 좌표 배포 | 시계가 시작된 뒤 히트박스를 내려줌 | 왕복 1회, 반응 즉시 | **정답 키가 기기에 올라간다.** 보고서의 "자동 이미지 비교" 치팅 대응과 정면 충돌 |
| (c) 탭 로그 사후 검증 | 완료 시 서버가 전부 재생 | 왕복 최소 | **실시간 피드백 불가.** 리빌 비행이 성립하지 않는다 |

### 판단

**(a)를 권한다.** 근거:

1. 대전 엔진이 이미 같은 결론에 도달했다. `MatchSnapshotV1`은 `claimed`에 **이미 획득한**
   목표의 원만 담고, 탭은 소켓 명령으로 간다. 학습 랭크드만 다르게 갈 이유가 없다
2. (b)는 이 프로젝트가 계속 지켜온 선을 넘는다. `production-boundary.test.ts`부터
   `registry.ts` 격리까지, "정답은 기기에 없다"가 일관된 원칙이었다
3. (c)는 §5.6의 리빌 비행을 죽인다. 이 문서가 최우선으로 꼽은 경험이다

지연 우려는 실측 후 판단한다. 틀린그림찾기는 탭 간격이 수 초 단위라 대전 게임만큼
민감하지 않다. 낙관적 UI(탭 즉시 링 표시 → 서버 확인 후 확정/철회)로 더 줄일 수 있다.

### 구현한 것

`POST /v1/learning/attempts/{id}/tap` — 마이그레이션 `202608140002`.

**일의 분할이 핵심이다.**

| 어디 | 무엇 | 왜 |
|---|---|---|
| `packages/contracts/src/learning-board.ts` | 기하 판정, 리빌 예산 | 클라이언트의 낙관적 링과 **같은 함수**를 서버가 쓴다. 판정이 둘로 갈리면 정상 탭이 깜빡인다 |
| SQL | 목표 존재 여부, 중복 클레임, 누적 카운트 | 부분 유니크 인덱스가 "한 차이는 한 번만"을 보장한다. API가 아니라 |

응답으로 나가는 것은 목표 id 하나, 그 원, 그리고 **글자 한 개**뿐이다.
`canonicalAnswer`와 나머지 히트박스는 API 프로세스에서 죽는다.

**부수적으로 신뢰 경계가 하나 닫혔다.** `commit_learning_attempt_owned_v1`이 이제
`wrong_taps`를 탭 로그에서 세고 요청 본문 값을 버린다. 첫 배선 때 "알려진 신뢰 경계"라고
적어둔 항목이다. `hints_used`와 `wrong_answers`는 아직 클라이언트 선언값으로 남아 있고,
각자의 서버 명령이 생길 때까지 그대로다.

부가로 정해진 것들:

- **탭에도 멱등키가 붙는다.** 응답이 유실돼 재시도하면 오답 한 번이 두 번 청구된다.
  같은 키는 저장된 결과를 그대로 돌려준다
- **이미 찾은 곳 재터치는 `DUPLICATE`**, 오답이 아니다. 실수 중 가장 흔한 더블탭에
  벌점을 물리면 정확도가 아니라 기억력을 벌하는 것이 된다
- **assets-ready 전 탭은 거부**(`ASSETS_NOT_READY`). 판을 다 풀고 나서 시계를 켜는 경로를 막는다
- 챌린지 목록이 `differenceCount` + 빈 슬롯 골격(`answerUnitCount`, `spaceIndexes`)을
  함께 준다. 정답 재료가 아니라 힌트 사다리 3단계(`ANSWER_LENGTH`)와 같은 정보다

### 검증 ✅ 완료

`pnpm check:db` 5단계 전부 통과 (Docker + Node 24.18.0, 로컬 Supabase).
pgTAP **347개 전부 통과**하며, 그중 새로 추가한 케이스는 다음과 같다.

| 케이스 | 결과 |
|---|---|
| 남의 attempt로 탭 / 보드 읽기 | `ATTEMPT_NOT_FOUND` — 존재 여부조차 확인해주지 않음 |
| `assets_ready_at`이 null인 attempt에 탭 | `ASSETS_NOT_READY` |
| 보드에 없는 목표 클레임 | `OBJECTIVE_NOT_FOUND` |
| 같은 목표 두 번 클레임 | 두 번째는 `DUPLICATE`, HIT 행은 하나 |
| 같은 멱등키 재호출 | 저장된 결과 반환, 행이 늘지 않음 |
| 오답만 wrong-taps를 올림 | 확인 |
| 커밋이 선언값 999를 버리고 로그의 1을 저장 | 확인 |
| 챌린지 목록에 정답·히트박스·목표 id 없음 | 확인 |
| `economy_server`의 비보호 함수 실행 권한 | 회수됨 |

**그 과정에서 잡은 실제 버그 네 개** — 정적 파서로는 잡히지 않던 것들이다.

| 버그 | 원인 |
|---|---|
| `pg_catalog.coalesce` 6곳 | `coalesce`는 SQL 구문이라 스키마 한정이 불가능하다. 기존 마이그레이션엔 없던 패턴을 내가 잘못 확장했다 |
| `force row level security` | 정책 없이 FORCE를 걸면 소유자까지 막혀 아무것도 못 쓴다. 저장소의 다른 테이블은 전부 `enable`만 쓴다 |
| 세 곳의 권한 허용목록 | `daily-pet-loop`·`rls`·`learning-competition` 테스트가 함수 집합을 고정해두고 있었다. **의도된 게이트가 제대로 작동했다** |
| 픽스처의 `private_solution`이 `'{}'` | 빈 해답으로는 탭 테스트가 엉뚱한 이유로 통과한다. 차이 2개와 정답을 넣었다 |

테스트 기대값을 세 번 틀린 것도 기록해둔다. `assets_ready_at`은 한 번만 쓰고 되돌릴 수
없어서(클록 되감기 방지 불변식) 백데이트가 아니라 실제 대기가 필요했고, 커밋을 즉시 하면
500ms 미만 안티치트가 격리한다. `'cat'`은 `'category'`의 부분 문자열이라 누출 검사 정규식이
자기 자신에 걸렸다.
