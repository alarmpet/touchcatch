## 요약 판정

**방향은 타당하나, 현재 파이프라인 그대로 500팩까지 스케일하면 반드시 깨진다.** 지금 26팩 기준으로도 이미 (1) 저장소 비대화, (2) 수작업 하드코딩 3곳, (3) 계획서와 코드의 파라미터 불일치가 관찰된다. 500팩은 이 문제들을 20배로 증폭시킨다. 아래 P0 항목을 1단계(`batch-build.js`) 착수 **전에** 해결할 것을 권한다.

## P0 — 스케일 전 반드시 선행

### 1. 저장소가 원본 PNG를 그대로 안고 간다 (가장 치명적)
`content/learning/source/`의 PNG는 장당 1.3–2.5 MB다. 계획의 1,000장이면 **약 2 GB가 git 히스토리에 영구 편입**된다. 게다가 `convert-png.js`는 원본 파일을 **제자리에서 덮어쓰므로**(`sharp(...).png()` → 같은 경로 `writeFile`) 재실행할 때마다 바이트가 바뀌어 SHA-256이 흔들리고, 그때마다 새 blob이 쌓인다.

- 권고: `source/`를 Git LFS로 옮기거나 `.gitignore` 처리하고, 저장소에는 **sha256 + 매니페스트만** 커밋. 실제 바이트는 외부 스토리지(Supabase Storage 등)에 두고 해시로 검증.
- 권고: 변환은 **비파괴적으로** — `raw/` → `source/` 단방향 출력. `10_CONTENT_AND_IMAGE_PIPELINE.md`의 "검증 뒤 원본 bytes를 바꾸면 안 된다"(REQ CONTENT-021)와 현재 in-place 덮어쓰기는 정면 충돌한다.

### 2. 계획서의 판정 반경 $r$ 값이 코드와 불일치
계획서는 난이도별 $r = 0.085 / 0.070 / 0.050$을 명시하지만, [auto-detect-delta.js](tools/content/auto-detect-delta.js)는 난이도와 무관하게 **`r: 0.065` 고정**을 출력한다. 실제 드래프트(`en-city-park`)는 또 `0.085`다 — 즉 사람이 중간에서 손으로 고치고 있다는 뜻이고, 500팩에서는 지속 불가능하다.

- 권고: 난이도 → $r$ 매핑을 카탈로그 단일 소스로 만들고, 탐지기가 `catalog.v1.json`의 `difficulty`를 읽어 $r$을 결정하게 할 것. 계획서의 표는 그 매핑의 문서 투영이어야 한다.

### 3. 검출기가 게시 게이트의 기하 규칙을 모른다
`CONTENT-017`은 **모든 objective 쌍의 overlap·tangent 금지**를 요구한다. 그런데 `findChangedRegions`의 클러스터링 임계값은 0.08이고 출력 $r$은 0.065 — 두 클러스터 중심이 0.081만 떨어져도 반경 0.065 원 두 개는 **겹친다**. 즉 자동 생성 결과가 validator에서 튕길 수 있으며, 이는 배치 실행 도중에야 발견된다.

- 권고: 탐지기 안에서 "중심 간 거리 > $2r$" 사후 필터를 넣고, 위반 팩은 즉시 `REJECTED` 사유와 함께 스킵 → 릴레이가 멈추지 않게.

### 4. `convert-png.js`의 파일명 하드코딩
26개 키가 소스에 배열 리터럴로 박혀 있다. 500팩이면 1,000줄짜리 배열이 되고, 매 세션 사람이 편집해야 한다. 계획의 "파일명만 넘기면"이라는 전제와도 어긋난다.

- 권고: `process.argv` 또는 `source/` 디렉터리 스캔 + 이미 변환된 항목 스킵(멱등).

## P1 — 500팩에서 반드시 병목이 되는 것

### 5. 모바일 레지스트리가 수동 `require` 나열
[registry.ts](apps/mobile/src/learning-demo/registry.ts)는 팩마다 `require('...json')` 한 줄씩 손으로 추가하는 구조다. 500팩 = **500줄 + 500개 JSON을 번들에 정적 포함**. Metro는 동적 `require`를 못 다루므로 코드 생성이 필요하고, 그와 별개로 번들 크기·초기 파싱 시간이 문제가 된다.

- 권고: (a) 레지스트리를 `batch-build`가 **생성**하게 하고 파일에 `// GENERATED` 마커 + drift 체크 추가(이 저장소가 이미 쓰는 패턴), (b) 장기적으로는 데모용 소수 팩만 번들에 넣고 나머지는 원격 카탈로그에서 로드.

### 6. `all-content.test.ts`가 스케일에 무의미해진다
현재 테스트는 `>= 9`와 전역 유일성만 본다. 500팩에서는 매 실행마다 500개 번들 + 500개 evidence를 JSON 파싱하며 느려지는 반면, 정작 잡아야 할 것(반경 정책 준수, hitbox 비겹침, 카테고리별 목표 개수)은 검사하지 않는다.

- 권고: 검사 항목을 위 3가지로 교체하고, 팩 단위 검증은 build 시점 evidence에 위임 + 테스트는 evidence 요약만 확인.

### 7. 이미지 중복/재사용 감지 장치 없음
동일 프롬프트를 반복 생성하다 보면 사실상 같은 그림이 다른 sha256으로 들어온다. 현재 유일성 검사는 **바이트 해시**뿐이라 이를 못 잡는다. 500팩 규모에서는 체감 품질을 직접 해친다.

- 권고: 지각 해시(pHash) 근접 검사 후 임계 이하면 경고.

### 8. CI 비용
`pnpm check`는 `content:validate` + 전체 vitest를 돈다. 2 GB 자산과 500팩이 붙으면 PR마다 체크아웃·설치·검증 시간이 수 배가 된다.

- 권고: 콘텐츠 검증은 `content/**` 변경 시에만 도는 별도 job으로 분리하고, 변경된 팩만 검증하는 증분 모드 추가.

## P2 — 계획 문서 자체의 공백

### 9. "무한 재플레이"(3장)의 구현 근거가 없다
"팩마다 15~20개 후보군, 세션마다 5~10개 무작위 추출"이라고 했지만, 현재 드래프트는 정확히 `difference_1..10` **고정 10개**이고 랜덤 샘플러의 소재지(클라이언트? 서버?)도 미정이다. 서버 권위 판정 구조라면 샘플링은 반드시 서버 측이어야 하며, 이는 계약(`PrivateGameSolutionV1`)과 DB 게시 함수에 영향을 준다 — 즉 **콘텐츠 생성이 아니라 계약 변경 작업**이다. 로드맵 1단계 앞에 별도 항목으로 올려야 한다.

### 10. 로드맵에 "게시" 단계가 없다
모든 드래프트가 `status: DRAFT`, `rightsReviewStatus/educationReviewStatus: REVIEW_REQUIRED`, `publishBlocked: true`다. `CONTENT-020`·`CONTENT-027`상 사람 승인은 **외부 blocker**다. 즉 500팩을 다 만들어도 **한 팩도 게시되지 않는다.** 계획서에 500건의 권리·교육 리뷰를 누가 어떤 속도로 처리하는지가 빠져 있고, 이것이 실질적인 최종 병목이다.

- 권고: 로드맵에 "5단계: 리뷰 처리량 설계(배치 승인 UI / 샘플링 감사 정책)"를 추가. 생성 속도를 리뷰 속도에 맞춰 조절하는 편이 낫다.

### 11. 드래프트에 절대 경로가 박혀 있다
`assetFiles`에 `D:\\touchcatch\\content\\...`가 들어간다. 다른 머신·CI에서 재현 불가하며, 로컬 디렉터리 구조가 저장소에 노출된다.

- 권고: 저장소 루트 기준 상대 POSIX 경로로 정규화.

### 12. 실패·재개 시맨틱 미정의
계정 교체 릴레이는 본질적으로 **중단이 잦은 장기 작업**인데, 429로 끊긴 세트의 부분 산출물(이미지 A만 생성됨 등)을 어떻게 처리할지 계획에 없다.

- 권고: `batch-build.js`를 완전 멱등(이미 완성된 팩은 스킵, 반쪽 팩은 정리 후 재시도)으로 설계하고, `manifest.v1.json`을 진행 상황의 단일 소스로 삼을 것.

## 권고 실행 순서

1. 자산 저장 전략 결정(P0-1) — 되돌리기 비용이 시간에 비례해 커지므로 최우선.
2. $r$ 매핑 단일화 + 비겹침 필터(P0-2, 3) — 배치 산출물의 게이트 통과율을 좌우.
3. 멱등 `batch-build.js` 작성(P0-4, P2-12) + 레지스트리 코드 생성(P1-5).
4. 리뷰 처리량 설계(P2-10)를 확정한 뒤에야 대량 생성 릴레이 개시.
